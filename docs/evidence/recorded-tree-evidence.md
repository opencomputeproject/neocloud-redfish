# Recorded-tree evidence — what shipping BMCs actually expose

Two BMC trees were recorded GET-only with a read-only account by the reference collector's recorder
(identities redacted, every metric value and firmware string preserved). They are held by the contributing
operator and will be published in DMTF mockup layout once a second unit per platform has been recorded.

| Recording | Platform | BMC firmware / Redfish | Recorded | Shape |
|---|---|---|---|---|
| `A1-01` | Supermicro H14DSG-OD + NVIDIA HGX B200 (Site A) | Supermicro BMC, Redfish 1.22.2, HMC 25.05 | 2026-08-10 | service root, Managers, Chassis, FirmwareInventory, platform tree, the 12 `HGX_*` MetricReports + definitions |
| `A1-69` | same SKU, HGX tray detached | as above | 2026-08-10 | 503 on every HGX path; Chassis 4 members, FirmwareInventory 24/0 |
| DELL-1 | Dell PowerEdge XE9680, 8× H100 (Site B) | iDRAC9 7.20.80.50, Redfish 1.20.1 | 2026-09-06 | 92-document mirrored tree: System, 10 Processors (8 GPU + 2 CPU) with ProcessorMetrics / MemoryMetrics / EnvironmentMetrics, DellGPUSensors, Chassis Power/Thermal/PowerSupplies, Storage, FirmwareInventory (120), TelemetryService after an operator change (5 MetricReports) |

A recording in DMTF mockup layout is served by the DMTF Redfish-Mockup-Server, so the DMTF Redfish-Interop-Validator
can be run against **real recorded responses** with no hardware and no credential (`tools/run-validator.sh`).

**Read the results correctly.** A recording holds only what the collector requested. A resource
the validator reports as *not found* (AccountService, EventService, SessionService, UpdateService,
Fabrics, ComponentIntegrity …) is *unrecorded*, not absent from the BMC — the unauthenticated
service root on both platforms advertises all of them (see `../research/bmc-unauthenticated-endpoints.md`).
Property-level results on recorded resources are real evidence.

## 2. What the recordings prove

1. **The NVIDIA HMC surface satisfies the draft's GPU RAS content almost entirely with standard schema** — `ProcessorMetrics` 14/15, HBM `MemoryMetrics.LifeTime` ECC, PCIe AER counters, throttle durations. The Supermicro BMC aggregates it into its own tree (no `AggregationService`, `AggregationService` 404s).
2. **iDRAC9 7.20 on the XE9680 exposes the same GPUs as standard `Processor`s but carries the RAS load in `Oem.Dell`/`Oem.Nvidia`** and has no HBM ECC over Redfish. A Mandatory `MemoryMetrics.LifeTime` is the right ask and Dell fails it today — that gap should be named to Dell, not hidden by demoting the requirement.
3. **Row remapping, NVLink error counters, throttle reasons and stale-value flags are `Oem.Nvidia` on every platform that has them.** These are the counters the fleet alerts on (`GPURemapBanksExhausted`, `NVLinkFlapping`, `GPUSustainedThrottle`). They are the DMTF schema proposals to open.
4. **`LinkStatus` reads `"OK"` on the HMC, not the DSP2046 enum `LinkUp`.** A profile that compares `LinkStatus` values must allow it, or the HMC must be fixed.
5. **`$expand` depth decides fleet-scale cost.** Dell MaxLevels=1 → per-resource walk → p50 6.7 s per node; Supermicro MaxLevels=3 + bulk reports → p50 1.8 s.
6. **Upstream profiles have defects a validator run exposes immediately:** `OCPServerHardwareManagement.v1_0_0.json` has `ProfileVersion "1,0,0"` (schema-invalid; validator aborts); Server 1.0.0 requires an `Intake` temperature context and SSH/IPMI serial console that a GPU server may not provide.
