### 3.3 Where to submit a Redfish profile
- **All OCP Redfish profiles live in the HM project** (its scope explicitly includes "Oversee the OCP's OCP-Profiles repository"). Domain profiles are developed in a **subfolder of `HWMgmt-OCP-Profiles`** by the owning workstream (e.g. `Server/`, `LiquidCooling/`, `RackAndPower/`), or in a workstream-owned repo (GPU profile now in `ocp-hm-system-gpu-management`), then **promoted to repo root once approved** ("promote approved profiles" PR #145, 2026-01-23). Each approved profile has a **Usage Guide** published through the OCP Contribution database (https://www.opencompute.org/contributions), authored in the OCP markdown template and rendered with `opencomputeproject/ocp-spec-tools` (see HFM README).
- The FTI workstream is a *forum*, not a spec owner: its own survey says the deliverable is an interop checklist plus "gap-ticket proposals into OCP HW Mgmt Project". FTI work "graduates" into a Project when it needs a spec.
- OCP contribution mechanics (https://www.opencompute.org/contributions/how-to-contribute ; governance https://www.opencompute.org/documents/ocp-governance-updated-june-1-2023 ; software process https://opencomputeproject.github.io/OCP-Software-GitHub-Process/software_contributions/): New Contribution Form → Contribution Hub workspace → abstract approved by Project Leads → CLA (OWFa 0.9 / modified OWF-CLA 1.0.2 for specs; CC-BY-SA 4.0 is used for usage guides and profiles today) → community review → Project Lead + IC representative endorsement → IC presentation. A "Contribution Taxonomy" draft effective 2026-06-10 exists (https://www.opencompute.org/documents/ocp-contribution-taxonomy).

## Implications for a neocloud Redfish profile

1. **Compose, don't duplicate.** Use `RequiredProfiles` to pull in `OCPBaselineHardwareManagement` (≥1.1.1, root of HWMgmt-OCP-Profiles) and `OCPServerHardwareManagement` (≥1.1.0, `Server/`, merged 2026-07-06), and consider `OCPServiceBaseline` 1.0.0 (Jeff Autor's service-level profile: EventService/EventDestination, TaskService, UpdateService, Certificates, RegisteredClient, `$only` mandatory). Baseline 2.0.0 is only a two-month-old draft — target 1.1.x and track 2.0.
2. **For the accelerator subsystem, require `OCP_UBB_BaselineManagement` v2.0.0** (https://github.com/opencomputeproject/ocp-hm-system-gpu-management/blob/main/profiles/OCP_UBB_BaselineManagement.v2.0.0.json) — it already mandates Processor/Metrics, Memory/MemoryMetrics, Port/PortMetrics, TelemetryService, LogService, PCIe inventory and `MultipartHttpPushUri`. Expect it to be renamed **UBB → "MAS"** (PR #64) — reference by ProfileName + MinVersion and be ready to rename.
3. **Venue = OCP Hardware Management project, Manageability Profiles workstream** (John Leung / Mike Raineri, `HWMgmt-OCP-Profiles`), with the System GPU Management workstream as co-reviewer for GPU resources. Develop in `neocloud-redfish` (or a `Neocloud/` subfolder PR to HWMgmt-OCP-Profiles), pair the JSON profile with an OCP-template **Usage Guide** rendered with `ocp-spec-tools`, then request promotion to repo root and Contribution-database publication. The FTI "Scaling AI Clusters at Neoclouds" workstream is the requirements source and sponsor (its March-2026 survey names "HW Mgmt & Interop" the #1 target with "gap-ticket proposals into OCP HW Mgmt Project"), not the approval body.
4. **Write the profile to DSP0272 1.10.0** (use `ProfileType`, `Priority`, `ErrorResponse`, `RequiredResourceProfile`, `UseCaseType` on ChassisType/ProcessorType) and validate with **Redfish-Interop-Validator 3.0.0 (2026-09-18)** or OCP's fork; fix the README's stale 1.4.0 pointer in the same PR series.
5. **Newer DMTF schema that a 2025 draft would miss:** `Protocol.NVLink/UALink/UET` and Port UALink/link-partner fields (2025.4–2026.2) for scale-up fabric ports; `PortMetrics.PCIeMetrics/ByLane` (2025.2); `Processor.ProcessorMemory` HBM3E/HBM4 (2025.4/2026.1) and `HardwareSecurityVersion` (2026.2); `LogEntry.DiagnosticDataType=Device` + `LogService.CollectDiagnosticData(TargetDevice)` (2025.1) for per-GPU dumps; `TelemetryService.CollectTelemetryData`/`TelemetryData` (2025.2) for raw device telemetry; `Status.Conditions[].ConditionType` (2025.2) and `VendorCode` (2026.2) for Xid-style vendor codes; the new **`Device` and `EventService` registries** (2026.2) for FRU/sideband faults and subscription-delivery failures; `Policy/PolicyService` and `PowerSubsystem.PowerBrake` (2026.2) for rack power capping; **resource aliases** (`~GPU_0`, DSP0266 1.25.0) to give stable names across OEM BMC trees.
6. **Codify the telemetry gap explicitly:** standard `ProcessorMetrics`/`MemoryMetrics` have ECC and throttle counters but no SM/tensor utilization, row-remapping, or Xid fields — these are `Oem.Nvidia`. The profile should require the standard fields as Mandatory and list the NVIDIA OEM fields (as observed in Lambda's exporter and NVIDIA/bmcweb) as Recommended "if the platform is HGX/MGX", and require MetricReportDefinitions such as `HGX_PlatformEnvironmentMetrics_0` / `HGX_ProcessorGPMMetrics_0` to be *discoverable* rather than hard-coding names.
7. **Events over polling:** require `EventService` with SSE and HTTPS push, `?includeoriginofcondition` (2025.1), prefix-based `RegistryPrefixes` subscriptions, and support for the standard registries (Base, Platform, Device, Fabric, NetworkDevice, Telemetry, Update, LogService, EventService) plus OCP's draft **`AcceleratorFabric`** registry (link flaps, retrain, packet-drop thresholds) — Microsoft's GS'25 talk documents event storms during GPU firmware pushes as a real hyperscale failure mode.
8. **RAS alignment:** cite OCP GPU & Accelerator RAS Requirements v1.7 (2025-10-23) and require CPER-carrying `LogEntry` (`CPER.SectionType`, `DiagnosticDataType=CPER/CPERSection/Device`, `AdditionalDataURI`) so NVIDIA's CPER-based *GPU Operational Events* (NVIDIA Event Section GUID) land in a standard place; track HFM issue #24 (Redfish schema for Status/Code-currency dumps) and the System Debug spec v0.1.
9. **Firmware:** mandate `MultipartHttpPushUri`, `UpdateServiceCapabilities`, staged/bulk activation (2025.2) and Update registry 1.4+/`NvidiaUpdate`-class messages; reference OCP GPU FW Update Requirements v1.1 and AMC spec v2.0 for BMC↔AMC expectations.
10. **Security posture:** require `ComponentIntegrity` (SPDM) for GPUs/ERoT where present (DGX GB200 exposes `Chassis/ERoT_BMC_0`, `HGX_ERoT_BMC_0`), `Manager.SecurityMode`, `CertificateService`/`CertificateEnrollment`, and account-security registry messages — aligned with OCP S.A.F.E./Attestation and the FTI survey's SPDM gap.
11. **Liquid-cooled GB200/GB300 racks:** include `LeakDetector`/`LeakDetection`, `Chassis.Links.LeakDetectors`, `CoolantConnector` metrics, `PowerSubsystem.PowerBrake` and rack-level `PowerDistribution`; compose `OCPLiquidCoolingBaseline` / `OCPCoolantDistributionUnit` (note issue #157 divergence from 2025.4) and `OCPRackManagerController` for NVL72 rack managers/NMX.
12. **Operational fields ClusterMAX rewards:** map the passive-check list (Xid/SXid, ECC, PCIe errors, link flaps, thermals) to Redfish Mandatory items so a profile-conformant BMC can back a ClusterMAX-grade passive health pipeline OOB; the GB200 bring-up requirement that every compute- and switch-tray BMC be discoverable argues for mandating SSDP/mDNS discovery and `Manager.ManagerType`/`Links.ManagerForChassis` completeness.
13. **Align with and cite what others published:** Lambda's `redfish_exporter` (the only neocloud OOB GPU collector, Apache-2.0), NVIDIA's OEM registries in `NVIDIA/bmcweb`, NVIDIA NICo/`nv-redfish`/`open-nvdebug` (Apache-2.0), Dell's iDRAC10 GPU telemetry report, and CoreWeave/Nebius health-check taxonomies; no Crusoe/Together/Vultr/Fluidstack public specs exist to align with.
14. **Aggregation semantics:** require the BMC to aggregate the HMC/AMC model per DMTF DSP2090 (as the System GPU spec v0.1 does) so `Systems/HGX_Baseboard_0` vs `Systems/System_0` splits are predictable to fleet tooling; DGX BMC docs still cite DSP0266 1.7.0/2019.1, so set a realistic `Protocol.MinVersion` (e.g., 1.15+) but make newer features conditional.
15. **Housekeeping before publishing:** `neocloud-redfish` is empty (no README/LICENSE/branches, one collaborator) — seed it with a CC-BY-SA 4.0 licence (matching existing profiles), README pointing to DSP0272 1.10.0 and the HM profile hierarchy, a `profiles/` JSON, a `docs/UsageGuide.md` in OCP template form, and an Interop-Validator config; open a tracking issue in HWMgmt-OCP-Profiles so the HM workstream sees it.
