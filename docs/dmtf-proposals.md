# Proposals to DMTF and OCP that the fleet evidence justifies

Everything the fleet alerts on that has **no standard home** today, with the evidence, the OEM property it
lives in now, and the proposed standard carrier. Ordered by operational weight.

| # | Signal | Where it lives today | Evidence | Proposal | Venue |
|---|---|---|---|---|---|
| 1 | **Accelerator subsystem availability** (tray/HMC unreachable while BMC healthy) | HTTP 503 on the subtree; `Manager` stays absent from any status | 2 incidents / 6 weeks; one undetected 9 days [live] | Require aggregated subordinate `Manager` members to report `Status.State=UnavailableOffline` and emit `Device.PresenceMismatch`-class or a new `AcceleratorSubsystemUnavailable` event. Clarify in DSP2090 (Aggregation Guidance for Compute Expansion Modules). | DMTF (DSP2090, Device registry) + OCP System GPU Mgmt |
| 2 | **HBM row remapping** (counts by kind, bank availability by class, pending, failed) | `MemoryMetrics.Oem.Nvidia.RowRemapping.*`, `RowRemappingFailed`; `Memory.Oem.Nvidia.RowRemappingPending` | 10 GPUs with remaps, 2 with no capacity left [live]; DCGM has `DCGM_FI_DEV_*_REMAPPED_ROWS`, `ROW_REMAP_FAILURE/PENDING` | Add `MemoryMetrics.RowRemapping {CorrectableCount, UncorrectableCount, Pending, Failed, BankAvailability{Max,High,Partial,Low,None}}` or map onto `HealthData.RemainingSpareBlockPercentage` + `AlarmTrips.SpareBlock` with defined semantics for HBM. | DMTF schema (MemoryMetrics) |
| 3 | **Scale-up link error counters** (link downed / unintentional down / recovery, symbol errors, effective BER, malformed packets, training/runtime errors) | `PortMetrics.Oem.Nvidia.*` on GPU and NVSwitch ports | NVSwitch link-down counters to 978 per switch; `NVLinkFlapping` alert [live] | Add a `PortMetrics.ScaleUp` (or extend `Networking`) block: `LinkDownedCount`, `UnintentionalLinkDownCount`, `LinkErrorRecoveryCount`, `SymbolErrorCount`, `EffectiveBER`, `RawBER`, `MalformedPacketCount`, `TrainingErrorCount`, `RuntimeErrorCount`. Port already has `PortProtocol=NVLink/UALink/UET` (2025.4–2026.2), so the protocol scoping exists. Pair with OCP `AcceleratorFabric` registry messages. | DMTF schema (PortMetrics) + OCP System GPU Mgmt registry |
| 4 | **Throttle reasons** (which limiter is active) | `ProcessorMetrics.Oem.Nvidia.ThrottleReasons[]`, plus HW/SW violation durations | `GPUSustainedThrottle` alert distinguishes thermal/HW-violation from power cap [live] | Add `ProcessorMetrics.ThrottleReasons[]` enum mirroring DCGM clock-event reasons (PowerCap, Thermal, HWSlowdown, HWThermal, HWPowerBrake, SWThermal, SyncBoost, AppClocks, Idle) and `HardwareViolationThrottleDuration`/`SoftwareViolationThrottleDuration`. `Processor.ThrottleCauses` exists (state, not duration). | DMTF schema (ProcessorMetrics) |
| 5 | **Per-value staleness in MetricReports** | `MetricValue.Oem.Nvidia.MetricValueStale`; report `Timestamp` null | 11 stale values dropped per fleet scrape; clients must not record them as fresh [live] | Add `MetricValue.Stale` (boolean) or require `MetricValue.Timestamp` and define staleness as a `Telemetry` registry message. | DMTF (MetricReport schema / Telemetry registry) |
| 6 | **Vendor RAS codes on events/log entries** (XID, SXID) | Free text inside `ResourceEvent.1.0.ResourceErrorsDetected` | 622 entries on one node; alerts cannot key on them [rec] | Adopt `VendorCode` (2026.2) on `LogEntry`/`Condition`/`Event` with a neutral `MessageId` from an accelerator RAS registry; OCP to publish that registry (this repo's `OCPAcceleratorRAS` draft + System GPU Mgmt `AcceleratorFabric`). | OCP System GPU Mgmt (registry) |
| 7 | **Link status enum drift** | HMC `Port.LinkStatus` = `"OK"` | Every NVLink port [rec] | Firmware conformance item for NVIDIA HMC; DMTF: consider documenting `LinkStatus` as the health of the link and leaving state to `LinkState`. | NVIDIA / OCP System GPU Mgmt |
| 8 | **Device left the bus but still enumerated healthy** | `Processor.Status` Enabled/OK with `PCIeInterface.LanesInUse=0` | A1-119 (4 of 8 GPUs off the bus, all OK); A1-96 (8 GPUs, 0 lanes) [rec, live] | Conformance guidance (DSP0266 §9.11 absent/transiently-unavailable resources): a device with no negotiated link is not `Enabled/OK`. | DMTF (DSP0266 guidance) + OCP RAS Requirements |
| 9 | **Firmware-band-dependent collection shape** | Report inventory and component counts change with HMC firmware (25 vs 34 members) | 3 bands in production [live] | Guidance in the OCP usage guide: clients discover collections and never hardcode counts; services keep member `Id`s stable across firmware. | OCP usage guide |
| 10 | **Fleet-scale query cost** | `ProtocolFeaturesSupported.ExpandQuery.MaxLevels` 1 vs 3; bulk reports OnRequest | 4x probe cost at MaxLevels=1 [live] | Profile requirement (done here); DMTF: consider an `excerpt`-style "telemetry" view for `Processor`/`Memory` collections. | This profile; DMTF |
| 11 | **Empty-bay vs failed PSU** | `PowerSupply.Status.State` Absent vs Enabled/Critical with ~5 W input | 6-bay/4-supply chassis; 13 dead supplies [rec, live] | Profile requirement (done here); `Device` registry (2026.2) `PresenceMismatch` is the right event. | This profile |
| 12 | **Unsynchronized manager clocks on event logs** | HMC EventLog entries at 2020-01-01 | [rec] | Require `Manager.DateTime` and a `ManagerEvent` message when time is not synchronized; clients sanity-check timestamps. | DMTF registry / profile |

- OCP System GPU Management (`ocp-hm-system-gpu-management`): items 1, 3 (registry half), 6, 7; convert `Redfish_Scale_Up_Fabric_Registry.md` to JSON (their issue #56) and add the accelerator RAS messages from `registries/OCPAcceleratorRAS.1.0.0.json`.
- OCP HFM (`OCP-HM-HFM-Hardware_Fault_Management`): their issue #24 (Redfish schema for status/code-currency dumps) is the place to attach items 6 and 8.
- NVIDIA: items 1 (HMC `Manager.Status`), 7 (`LinkStatus`), 5 (`MetricValueStale` → standard) through the System GPU Management workstream, where NVIDIA co-leads.
